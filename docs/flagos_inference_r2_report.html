逐算子：实现、调用与结论

下面只列本轮可由真实 SToFM profiler 和端到端基准证明的内容。所有源码链接都指向两个已推送的 fork。

Gaussian pair bias

flagos_stofm::gaussian_pair_bias

将距离仿射、RBF 构造、两层投影、ReLU、head 排布和零距离置零作为一个 SToFM 复合边界注册。CUDA 推理使用 Triton；CPU、Autograd 和不满足输入约束的 CUDA 输入回到参考实现。

  • 真实模型调用：SToFM Gaussian 模块
  • 注册 ABI：FlagGems custom operator
仅该算子，关闭 ATen 接管 1.321x / 1.436x

FP32 / FP16 均达到独立晋升阈值，是组合路线的主要收益来源。

Pair-score epilogue

flagos_stofm::pair_score_epilogue

将 score 构建后的 padding mask、softmax、可选 pair-state 与 attention weights 返回保持为单一公开 ABI。原生 CUDA 路径仅用于连续 FP32/FP16 推理输入；dropout、训练、非连续布局与超出长度约束的输入回退到参考实现。

  • 模型桥接：SToFM FlagOS bridge
  • NVIDIA 后端：Triton pair-score kernel
仅该算子，关闭 ATen 接管 1.055x / 1.015x

FP16 独立收益不足 1.05x；不单独宣传，但在已验证的双算子组合中保留。

双算子组合

gaussian_pair_bias + pair_score_epilogue

这条路线关闭普通 FlagOS ATen 接管，因此 profiler 中出现的两个事件和端到端收益都可以直接归因于本轮注册算子。它是对“是否真的补齐算子”的核心回答。

  • FP32 与 FP16 都保存 3 轮独立进程的原始 JSON、CSV、日志和 SHA-256 manifest
  • 结果验证器检查每一轮的 custom-op trace、源码根和 30 个样本
只使用新注册算子 1.566x / 1.690x

FP32 / FP16；这是本页最直接的新算子端到端性能结论。

Marker-token embed

flagos_stofm::marker_token_embed

FlagGems 已把 marker-token assembly 注册为同一命名空间的 CUDA/CPU/Autograd ABI，并有 profiler 测试。但当前工作区不存在可直接修改的真实 Uni2/KRONOS 模型调用点，因此不把旧的独立 Vision 边界数字写成真实模型收益。

  • Vision 公共接口：marker-token dispatch
  • 注册 ABI：shared operator registry
当前状态 已注册，待模型接入

有 CUDA 正确性与 profiler 证据；没有 Uni2/KRONOS 端到端性能声明。

Ascend 310 与 MTT S4000：为租赁而准备，不预报性能

目标设备代码已被设计为与 V100 使用同一公开 ABI，但只有离线静态验证通过。真实编译、正确性矩阵与性能数据必须在租赁设备上重新采集。

目标 当前已完成 租赁设备上的第一步 可发表性能的门槛
Ascend 310 / CANN Gaussian 与 pair-score 的延迟 AscendC 源码、host registration、精度分发、schema/CMake/C++ 静态检查。 用真实 CANN SDK 编译并确认 torch.ops.flagos_stofm 注册，再跑 FP32/FP16/BF16 正确性矩阵。 重新采集目标自身的纯 PyTorch、未优化 FlagOS、仅新算子、组合路线；不得复用 V100 数字。
MTT S4000 / MUSA 共享 ABI 的 PrivateUse1 延迟扩展、MUSA kernel、Triton 候选、schema/CMake/C++ 静态检查。 用真实 MUSA SDK 构建扩展并确认 ABI，逐精度测试连续输入、mask、padding 与安全回退。 按 MTT 自身未优化 FlagOS 基线计算；仅在 Gaussian ≥1.15x、pair-score ≥1.05x、双算子端到端 ≥1.10x 且语义通过时晋升。

本报告只使用可追溯的 V100 原始样本和已推送的源码。它不把编译器优化、普通 ATen 接管、注册算子、未实测目标设备混为同一类结论。

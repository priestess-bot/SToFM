FlagOS Inference R2
SToFM、Uni2 与 KRONOS 的 V100 技术评审

这不是“把编译器改名为 FlagOS”的性能展示。报告将纯 Torch、冻结未优化 FlagOS 与优化后 FlagOS 分开测量，明确指出哪些是已实测的后端能力，哪些是被拒绝的候选，以及 Ascend/MTT 目前只完成到什么程度。

这份报告回答三件事

  • 冻结 FlagOS 本身带来了多少、以及测量边界在哪里。
  • 哪些复合算子在 V100 上真正值得进入优化路径。
  • 国产芯片代码已经准备到何种可验证状态，哪些结论尚不能作出。
设备 Tesla V100-SXM2-16GB / CUDA 12.4 / PyTorch 2.6.0 精度 FP32、FP16 独立测量 样本 3 个独立进程，90 个原始 CUDA-event 样本 / 阶段 SToFM fork FlagGems fork

先统一三条基线

所有速度比必须说明相对哪一条基线；端到端消融与独立 Vision 算子边界不会混写。

P1 / TORCH 规范纯 PyTorch

不返回未使用的最终 pair_rep，是端到端的可比较参考实现。

F0 / FROZEN FLAGOS 冻结提交的 scoped ATen 路由

应如何理解“FlagOS”

F0 不是空壳，也不是全模型后端。 它是真实的、临时 scoped flag_gems.use_gems() 路由， 覆盖 addmm、baddbmm、bmm、softmax。 R2 在这个冻结基线之上补齐明确的复合边界。Vision 的 F0 worker 使用冻结包、复现同等验证和 dispatch 开销，但不导入 R2 Vision API。

严格验证

为什么这些数字可以被复查

测试不是单次截图：环境、reference hash、测量控制、独立 worker、原始样本和 checksum 都被保留。任何跨环境 workload、timer 或 runtime identity 漂移都会被聚合器拒绝。

01

固定工作负载

SToFM 使用 B=1、N=1050、L=4、D=256、FFN=256、H=8、K=128；Vision 边界使用各自固定真实形状。

02

先验正确性

每个候选先与 Torch assert_close；FP32 为 rtol 3e-4 / atol 3e-5，FP16 为 rtol 3e-2 / atol 3e-3；marker mask 必须精确相同。

03

独立进程计时

每精度 3 个独立进程；10 次 warm-up、30 个 CUDA-event sample、每 sample 5 次调用。编译只在 warm-up 中发生。

04

统计与可追溯

每阶段 90 个原始样本，10,000 次 bootstrap 得到 95% CI；运行记录 pip freeze、GPU、driver、Torch backend 与环境变量。

26

FlagGems R2 回归通过：precision、shape、mask、padding、non-contiguous fallback、gradients 与 target static gate。

28

SToFM 优化环境测试通过：三模式、双环境聚合、profile 分类、dispatch cleanup 与 checksum 验证。

3

冻结环境测试通过：P1 语义等价与不导入 R2 Vision API 的 F0 worker。

结论的边界条件

  • V100 数字只适用于本报告声明的 synthetic SToFM 输入与 Vision 算子边界，不等价于完整 Uni2/KRONOS 模型吞吐。
  • 峰值 allocation 仅是 timed window 内的增长，不是总进程或模型显存。FP32 的 P1/F0 为 1618.09 MiB，Ffinal 为 145.15 MiB；FP16 分别为 1617.07 MiB 与 71.40 MiB。
  • Ascend 310 与 MTT S4000 在完成实际 SDK 构建、正确性矩阵与 P1/F0 建立前，页面不包含任何目标性能数字。

目标设备计划

租赁 Ascend / MTT 后，如何把“源码已备”变成可比较结果

现在的 target 代码刻意不依赖真实芯片就能通过静态门禁；上机时应先建立目标自己的 P1/F0，再逐个启用已准备的边界。所有阈值均是计划门槛，不是预先声称的性能。

Ascend 310 / CANN

已有：Gaussian 与 pair-score 的 AscendC host/kernel/tiling/dtype dispatch，lazy adapter 与 reference fallback。
待实机：实际 ASCEND_NPU_ARCH 构建、FP32/FP16/BF16 语义矩阵、P1/F0 与性能证据。

MTT S4000 / MUSA

已有：MUSA extension、.mu Gaussian/pair kernels、PrivateUse1 schema、lazy Triton/extension selection。
待实机：mcc SDK 构建、dtype/mask/padding/non-contiguous 语义矩阵、P1/F0 与性能证据。

计划阈值

相对各目标自己的 F0：Gaussian 至少 1.15x、pair 至少 1.05x、marker 至少 1.05x，端到端至少 1.10x；否则保留 fallback 或标为 rejected。

  1. 记录租赁机型、driver、SDK、Torch 扩展、编译命令与 Git SHA；先运行 deferred target gate，确认 lazy import 没有掩盖环境错误。
  2. 对每种支持 dtype 跑 Torch reference 与 target fallback/native 的 shape、mask、padding、pair-state、non-contiguous、gradient 矩阵；任何不一致先停止性能工作。
  3. 分别测目标 P1、真实 scoped F0、每个 promoted candidate 与最终组合；沿用 3 个独立进程、warm-up、90 原始样本和 bootstrap CI。
  4. 保存 JSON、CSV、日志、trace 与 checksum，更新 checklist 后再把 target 数字放进本报告；未跨阈值的路线写为 reject 或 retain fallback。

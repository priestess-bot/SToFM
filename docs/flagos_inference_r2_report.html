FlagOS 推理优化
SToFM、Uni2 与 KRONOS 的 V100 技术评审

这不是“把编译器改名为 FlagOS”的性能展示。报告将纯 PyTorch、固定版本的未优化 FlagOS 与优化后 FlagOS 分开测量，明确指出哪些是已实测的后端能力，哪些是被拒绝的候选，以及 Ascend/MTT 目前只完成到什么程度。

这份报告回答三件事

  • 冻结 FlagOS 本身带来了多少、以及测量边界在哪里。
  • 哪些复合算子在 V100 上真正值得进入优化路径。
  • 国产芯片代码已经准备到何种可验证状态，哪些结论尚不能作出。

应如何理解“FlagOS”

未优化 FlagOS 基线不是空壳，也不是全模型后端。 它会在一次指定推理区间内临时启用 flag_gems.use_gems() 算子路由， 覆盖 addmm、baddbmm、bmm、softmax。 优化后 FlagOS 在这个固定版本基线之上补齐明确的复合边界。Vision 的未优化基线计时进程使用固定版本包、复现同等验证和路由开销，但不导入新版 Vision API。

严格验证

为什么这些数字可以被复查

测试不是单次截图：环境、基准输出哈希、测量控制、独立计时进程、原始样本和校验和都被保留。任何跨环境工作负载、计时器或运行时身份漂移都会被聚合器拒绝。

01

固定工作负载

SToFM 使用 B=1、N=1050、L=4、D=256、FFN=256、H=8、K=128；Vision 边界使用各自固定真实形状。

02

先验正确性

每个候选先与纯 PyTorch assert_close；单精度 FP32 为 rtol 3e-4 / atol 3e-5，半精度 FP16 为 rtol 3e-2 / atol 3e-3；marker mask 必须精确相同。

03

独立进程计时

每种精度使用 3 个独立进程；10 次预热、30 个 CUDA-event 样本、每个样本 5 次调用。编译只在预热中发生。

04

统计与可追溯

每阶段 90 个原始样本，10,000 次自助法重采样得到 95% 置信区间；运行记录软件包版本、GPU、驱动、PyTorch 后端设置与环境变量。

26

FlagGems 优化版回归通过：精度、形状、掩码、padding、非连续输入回退、梯度与目标设备静态检查。

28

SToFM 优化环境测试通过：三种模式、双环境聚合、性能跟踪分类、路由清理与校验和验证。

3

固定版本环境测试通过：纯 PyTorch 语义等价，以及不导入新版 Vision API 的未优化 FlagOS 计时进程。

结论的边界条件

  • V100 数字只适用于本报告声明的合成 SToFM 输入与 Vision 算子边界，不等价于完整 Uni2/KRONOS 模型吞吐。
  • 峰值内存分配仅是计时窗口内的增长，不是总进程或模型显存。单精度中，纯 PyTorch/未优化 FlagOS 为 1618.09 MiB，优化组合为 145.15 MiB；半精度分别为 1617.07 MiB 与 71.40 MiB。
  • Ascend 310 与 MTT S4000 在完成实际 SDK 构建、正确性矩阵与纯 PyTorch/未优化 FlagOS 基线建立前，页面不包含任何目标性能数字。

目标设备计划

租赁 Ascend / MTT 后，如何把“源码已备”变成可比较结果

现在的目标设备代码刻意不依赖真实芯片就能通过静态门禁；上机时应先建立该设备自己的纯 PyTorch 与未优化 FlagOS 基线，再逐个启用已准备的边界。所有阈值均是计划门槛，不是预先声称的性能。

Ascend 310 / CANN

已有：Gaussian 与 Pair-score 的 AscendC 主机代码、内核、分块与数据类型分发，按需加载适配器与参考实现回退。
待实机：实际 ASCEND_NPU_ARCH 构建、单/半/BF16 语义矩阵、纯 PyTorch/未优化 FlagOS 基线与性能证据。

MTT S4000 / MUSA

已有：MUSA 扩展、.mu Gaussian/Pair 内核、PrivateUse1 接口定义、按需 Triton/扩展选择。
待实机：mcc SDK 构建、数据类型/掩码/padding/非连续输入语义矩阵、纯 PyTorch/未优化 FlagOS 基线与性能证据。

计划阈值

相对各目标自己的未优化 FlagOS 基线：Gaussian 至少 1.15x、Pair 至少 1.05x、marker 至少 1.05x，端到端至少 1.10x；否则保留参考实现回退或明确标记为不采用。

  1. 记录租赁机型、驱动、SDK、PyTorch 扩展、编译命令与 Git SHA；先运行目标设备预检查，确认按需导入没有掩盖环境错误。
  2. 对每种支持的数据类型运行纯 PyTorch 参考实现与目标设备参考/原生路径的形状、掩码、padding、pair-state、非连续输入、梯度矩阵；任何不一致先停止性能工作。
  3. 分别测目标设备的纯 PyTorch、真实未优化 FlagOS、每个待采用候选与最终组合；沿用 3 个独立进程、预热、90 原始样本和自助法置信区间。
  4. 保存 JSON、CSV、日志、性能跟踪与校验和，更新实施清单后再把目标设备数字放进本报告；未跨阈值的路线写为不采用或保留参考实现回退。
